# Luckinit PRD

## 产品定位

Luckinit 是一个内部地图分析与选址辅助工具，当前主要服务于：

- 北京写字楼点位查看与筛选
- 城市热点与商业聚集度观察
- 北京候选商圈与品牌落点辅助判断

系统以网页形式提供能力，统一登录后进入不同功能页面。后端由 `main.py` 提供 API，数据主要保存在 `cache.sqlite3`。

## 当前产品结构

### 统一入口

- `index.html`
  登录页与页面选择页。

### 功能页面

- `city_analysis.html`
  城市热点分析页面。
- `mengniu_beijing.html`
  北京候选点与商圈分析页面。
- `beijing_office_map.html`
  北京写字楼地图页面。

### 后端

- `main.py`
  登录鉴权、页面路由、地图代理、数据查询和热力图 API。

### 数据与脚本

- `cache.sqlite3`
  SQLite 数据库。
- `logs/`
  服务日志目录，保存应用日志与访问日志。
- `scripts/import_beijing_office_buildings.py`
  北京写字楼 Excel 导入脚本。
- `scripts/fill_beijing_office_coordinates.py`
  写字楼坐标补齐脚本。
- `scripts/manage_accounts.py`
  账号管理脚本。

## 登录与权限

- 首页是统一登录入口。
- 登录成功后可以进入正式功能页面。
- 其他页面未登录会跳回首页。
- 会话信息保存在 SQLite 的 `users` 和 `sessions` 表中。

## 北京写字楼地图

### 页面目标

- 按区域查看北京商场与写字楼分布
- 在高德地图上展示楼宇点位
- 按点位类型区分视觉颜色，便于快速识别商场与写字楼
- 查看每栋楼的业务参数
- 通过推荐度快速识别更值得关注的楼宇
- 通过热力图辅助判断区域热度和人流代理强弱

### 点位数据

数据来源：

- `docs/北京大区整理数据3.31.xlsx`

主表：

- `beijing_office_buildings`

当前导入范围：

- `大位置类型 = 写字楼`
- `大位置类型 = 商场`
- 其余类型（如交通枢纽）默认不导入当前地图页

主要字段包括：

- 楼宇名称、区域、类型、二级类型
- 推荐状态
- 已开业门店数
- 工作人数
- 客流类指标
- 师生规模类指标
- 日均外送现制商品数
- 坐标字段

坐标采用双轨保存：

- `longitude` / `latitude`
  WGS84，用于通用分析与导出
- `gcj02_longitude` / `gcj02_latitude`
  GCJ-02，用于高德地图展示
- 坐标补齐脚本默认只处理缺失坐标的点位，避免重复全量请求外部地图服务
- 对非北京市区县（如廊坊市广阳区、三河市）会按区县自动切换查询城市，减少外圈点位漏匹配

### 地图展示规则

- 地图点位按 `location_type` / `location_subtype` 自动区分颜色
- 商场类点位使用橙色系
- 写字楼类点位使用青绿色系
- 地图右侧区域提供简易图例，帮助用户理解颜色含义
- 左侧列表同步显示类型标签，保持地图与列表的视觉一致性

## 热力图逻辑

### 核心原则

当前热力图不是“真实客流统计图”，而是“开源人流代理热力图”。

它的作用不是给出精确客流人数，而是帮助用户快速识别：

- 交通更强的区域
- 商业更密集的区域
- 更可能形成稳定人流聚集的区域

### 数据来源

热力图数据来自：

- OpenStreetMap
- Overpass API

### 纳入的人流代理信号

- 地铁口
- 地铁站
- 公交站 / 公交枢纽
- 商场 / 百货 / 集市
- 超市 / 便利店
- 餐饮 / 咖啡 / 奶茶 / 烘焙
- 写字楼 / 商务中心
- 学校 / 大学
- 影院 / 剧院

### 权重设计

不同 POI 对人流代理强度的贡献不同，因此采用加权逻辑：

- 地铁口、地铁站权重最高
- 商场和大型商业节点权重较高
- 公交、餐饮和便利零售为中等权重
- 办公、学校和文娱设施为辅助权重

规则定义位置：

- `main.py` 中的 `BEIJING_FLOW_PROXY_RULES`

### 网格聚合

后端不会直接把每个 POI 单独画出来，而是先进行约 `250 米` 的网格聚合：

- 同一格中的权重累加形成 `weight`
- 同时记录 `poi_count`
- 每个网格输出为一个热力单元

这样做的目标是：

- 降低前端绘制压力
- 保持热力图连贯性
- 更适合区域级观察

### 前端渲染

前端在 `beijing_office_map.html` 中使用 `canvas` 叠加层绘制热力图。

渲染特性：

- 热力图位于底层
- 楼宇标注位于热力图上层
- 热力图不拦截鼠标交互
- 当前使用火焰风格配色：
  - 亮黄
  - 橙色
  - 红色
  - 暗褐色

强度逻辑：

- 按当前批次热力单元的最大 / 最小权重做归一化
- 权重越高，颜色越亮、扩散半径越大

## 热力图缓存与性能

为了提升加载速度，当前采用两层缓存：

### 通用缓存

- SQLite 表：`cache`
- 保存整包 JSON 数据

### 专用热力表

- SQLite 表：`beijing_flow_heatmap_cells`

该表保存热力网格单元，包括：

- 区域
- 类别
- 权重
- POI 数量
- 示例名称
- WGS84 坐标
- GCJ-02 坐标
- 更新时间

设计目标：

- 避免每次页面访问都重新请求 Overpass
- 提高按区读取速度
- 为后续热力图扩展打基础

## 当前限制

- 热力图不是运营商级真实客流，只是开源代理热度
- Overpass 属于公共服务，稳定性会受外部网络影响
- 部分页面和逻辑还在持续整理
